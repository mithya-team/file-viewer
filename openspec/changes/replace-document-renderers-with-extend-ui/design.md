## Context

`FileViewer` already provides the stable package boundary: it buffers every source to a `Blob`, detects the kind from loaded data, owns fallback/error state, and exposes format-specific chrome APIs. The current internal implementations use `pdfjs-dist`, `docx-preview`, SheetJS, and Pagus. In particular, PDF and PPTX have package-owned page, zoom, and settled-navigation semantics that external consumer chrome relies on.

Extend UI is a source-distributed UI kit, not one installable viewer runtime. Its supplied viewer shells bring a separate toolbar, thumbnails, Coss-style primitives, and assumptions about URL inputs. Its underlying renderer packages are the appropriate integration boundary for this library:

- PDF: EmbedPDF packages used by Extend UI.
- DOCX/DOTX: `@extend-ai/react-docx`.
- XLSX/XLS: `@extend-ai/react-xlsx`.
- PPTX/POTX: `@extend-ai/react-pptx`.
- CSV: Extend UI's Papa Parse and Glide Data Grid stack.

The published Extend PDF helper fetches PDFium WASM from jsDelivr. That is incompatible with an air-gapped runtime and with this package's rule that package-owned renderer assets must not require consumer copying. The published CSV surface also requires browser-only Glide loading and vendor CSS, so it cannot be statically imported from the SSR-safe package entry.

## Goals / Non-Goals

**Goals:**

- Keep the public `FileViewer` props, content-driven detection order, and normalized `Blob` renderer input contract unchanged.
- Replace the five requested renderer implementations with pinned Extend-stack primitives behind internal adapters.
- Make PDF rendering work with no runtime CDN request; workers, WASM, and required styles must be carried or resolved by the installed package artifact.
- Keep `FileViewer` as the only built-in toolbar and download owner. Vendor toolbars and thumbnail rails are disabled.
- Preserve workbook sheet controls and PDF/PPTX page, zoom, `geometryReady`, and latest-request-wins `subscribePageNavigate` behavior for consumer-owned chrome.
- Preserve the exported `PdfRendererProps` search query, search-state, active-match, and request-page callback behavior without retaining pdf.js-specific text-layer markup.
- Preserve DOCX/DOTX and PPTX/POTX static preview scope; never use filenames or consumer MIME intent for routing.

**Non-Goals:**

- Add a public thumbnail-sidebar option, editing, annotations, rotation, upload controls, animations, presenter mode, legacy PPT routing, or custom renderer registration.
- Add progressive source loading, server-side conversion, or a fallback network CDN.
- Copy the full Extend registry viewer shells or adopt their Coss UI primitives as a runtime dependency.
- Change the `FileKind` or make XLS/PPT legacy detection broader than the existing content-driven format scope.

## Decisions

### 1. Build small internal adapters on the renderer primitives

Each replacement renderer remains an internal component receiving a normalized `Blob` and reporting the same shell callbacks. It uses the underlying Extend-stack library rather than importing a copied registry shell. This avoids duplicated toolbars, thumbnails, URL/upload state, and unrelated Coss UI primitives.

| File kind | Internal adapter | Renderer primitive | Input conversion |
|---|---|---|---|
| PDF | `PdfRenderer` | EmbedPDF | Package-owned `blob:` URL |
| DOCX/DOTX | `DocxRenderer` | `@extend-ai/react-docx` | `File` created from buffered blob |
| XLSX/XLS | `SpreadsheetRenderer` workbook branch | `@extend-ai/react-xlsx` | `ArrayBuffer` from buffered blob |
| CSV | `SpreadsheetRenderer` CSV branch | Papa Parse + Glide Data Grid | Decoded text from buffered blob |
| PPTX/POTX | `PptxRenderer` | `@extend-ai/react-pptx` | `File` or package-owned `blob:` URL |

The adapter boundary preserves detection and never uses the generated generic display filenames for routing. Generic names are display/download metadata only when a lower-level renderer requires one.

**Alternative considered:** install `@extend/*` registry components unchanged. Rejected because the registry expects source copying, owns its own chrome, does not expose all required FileViewer state, and adds a second design system to a library that already owns its primitives.

### 2. PDFium is an installed-package asset, never a CDN default

The PDF adapter SHALL construct the EmbedPDF engine with a Vite-emitted local PDFium WASM URL. Its worker implementation and WASM binary will be emitted or referenced from the package build using package-relative, bundler-managed URLs. The installed artifact must work when all external network requests are denied.

The implementation will use the package-supplied PDFium asset/export where possible rather than copying binary assets into application source. If the engine needs an explicit asset URL, the helper stays internal and receives the URL generated by the package build.

**Alternative considered:** expose a public CDN/asset URL configuration and keep jsDelivr as the default. Rejected because the safe default must be air-gap capable; consumer configuration may be considered later only as an override, never as a required step.

### 3. FileViewer remains the page/zoom/navigation authority

Vendor toolbars, upload buttons, downloads, and thumbnail rails are disabled. `FileViewerDefaultChrome` and custom `FileViewerChromeApi` consumers remain the only controls exposed by this package.

For every PDF/PPTX `setPage` call, the shell increments its existing navigation intent even when the requested page is already current. The renderer records the intent token and target, calls the underlying imperative control, and waits for the target to become active and the scroll to settle. Native `scrollend` is used when available, with a bounded scroll-idle fallback for evergreen browsers that lack it. A new command supersedes any older pending token, so only the newest target may emit `subscribePageNavigate({ page, reason: "programmatic" })`.

- PDF bridges `PDFViewerHandle.scrollToPage`, active-page reporting, document-load page count, and controlled zoom through EmbedPDF's capability API.
- PPTX uses `@extend-ai/react-pptx`'s controller `goToSlide`, `onLoad`, `onReady`, `onSlideChange`, controlled `zoom`, `showToolbar={false}`, and `showThumbnails={false}`.

`geometryReady` becomes true only after the underlying renderer has a usable scroll viewport/controller. It is reset on a new blob or renderer error.

**Alternative considered:** expose vendor chrome and remove FileViewer's PDF/PPTX controls. Rejected because it is a breaking change to external chrome integrations and does not meet citation/page-jump use cases.

### 4. Spreadsheet uses the lower-level Extend workbook surface; CSV stays a separate text adapter

The XLSX/XLS adapter uses `XlsxViewerProvider`, `XlsxViewer`, and the controller/hooks that Extend's own wrapper uses. It owns workbook buffer loading, translates sheet metadata and active-sheet commands to `FileViewer` callbacks, and does not mount the vendor toolbar.

CSV does not pass through workbook parsing. Its adapter reads the buffered `Blob` into a string, first recognizing UTF BOMs and an explicitly available charset before falling back to UTF-8. It passes the decoded text to the CSV viewer and reports decode/parser/render failures through the existing render-error path. CSV remains a single-sheet spreadsheet with no workbook chrome.

Glide Data Grid is loaded only from a client-rendered CSV submodule. Its third-party CSS is imported by that same dynamically loaded submodule, so the built package emits a relative CSS chunk; it is not copied into a consumer's `public` directory or written as a new hand-authored renderer stylesheet.

**Alternative considered:** retain SheetJS for XLS and CSV compatibility. Rejected as the default architecture because it leaves the renderer replacement incomplete; the implementation gate includes fixture tests proving XLS compatibility before removing it.

### 5. PDF search remains behaviorally compatible but engine-owned

`PdfRendererProps` and the exported PDF search types remain available. The adapter translates `searchQuery` to EmbedPDF's search capability, maps result counts/active-result state back through `onSearchStateChange`, and invokes `onRequestPageForSearch` when the active result is on another page. The underlying engine owns text selection and highlight markup; this package no longer depends on pdf.js line divs or word-span data attributes.

**Alternative considered:** remove the search renderer props because `FileViewer` does not currently expose search controls. Rejected because those types and callback semantics are documented exports and a renderer replacement must not silently make them inert.

### 6. DOCX remains blob-first and preserves the supported document scope

The DOCX adapter receives a buffered `Blob`, creates an in-memory `File` for the lower-level renderer, and disables its vendor chrome. DOTX continues through this path. The old `docx-preview`-specific layout-correction helpers are removed only after fixtures demonstrate that anchored images, right-aligned header imagery, and behind-document backgrounds satisfy the retained visual requirements.

**Alternative considered:** embed the full `DocxViewerPreview` registry component. Rejected because it requires library-owned dark-theme controls and a separate toolbar that are not part of FileViewer's API.

### 7. Pin the minimal direct rendering stack and validate it in the built package

The initial versions are the versions used by the current Extend UI source: EmbedPDF `2.14.4`, `@extend-ai/react-docx@0.8.2`, `@extend-ai/react-xlsx@0.16.1`, and `@extend-ai/react-pptx@0.1.2`. The exact direct PDFium asset package and CSV dependency versions are resolved through the package manager during implementation, pinned in the lockfile, and kept limited to what the adapters import.

The implementation validates SSR import separately from client rendering. In particular, Glide's browser-only module must not enter the package entry's server evaluation path. The build verification gains checks for emitted local PDF runtime assets and CSS references; browser tests deny network access while rendering PDF.

## Risks / Trade-offs

- **[PDFium asset resolution differs by bundler]** → Verify Vite emits both worker and WASM from the installed artifact, and add an offline browser test before removing pdf.js.
- **[Extend UI's CSV stack currently uses an alpha Glide release]** → Pin the compatible version, isolate it to the lazy CSV module, and cover large-table, parsing, and SSR-import smoke tests.
- **[XLS compatibility is weaker than XLSX]** → Gate SheetJS removal on an XLS fixture and test formula/value, sheet names, and rendering; report a render fallback if an otherwise detected XLS cannot be parsed.
- **[Lower-level controls do not directly expose current settled-navigation semantics]** → Implement the token/target/scroll-idle bridge and test repeated same-page, rapid successive, and source-change navigation.
- **[DOCX fidelity differs from docx-preview]** → Retain existing visual fixtures and add a direct acceptance test for the layout guarantees before deleting correction helpers.
- **[Bundle size increases]** → Measure built artifact size and dynamic-load CSV; avoid registry shells and unrelated icon/primitives dependencies.
- **[Vendor CSS conflicts with host Tailwind]** → Limit CSS to the client CSV path, document it in the package style entry, and keep FileViewer layout/token classes authoritative.

## Migration Plan

1. Add pinned primitive dependencies and package-owned asset/build support while retaining the current renderers as the test baseline.
2. Implement and validate the PDF adapter offline, including navigation and installed-artifact checks.
3. Replace PPTX with the controlled, thumbnail-free Extend primitive adapter and update the Pagus invariant.
4. Replace DOCX and workbook XLSX/XLS paths after their fidelity/compatibility fixtures pass.
5. Add the lazy CSV text adapter, vendor-style emission, and SSR import coverage.
6. Remove superseded dependencies and renderer helpers only after package, demo, unit, built-artifact, offline, and source-mode tests pass.

Rollback is a normal package-version rollback: restore the previous renderer dependencies and internal renderer implementations together. No public data migration or persisted state is involved.
